# Управление секретами и сертификатами

Документ подготовлен на основе `DOC.md` и описывает управление секретами и сертификатами в PVS простым языком.

## 1. Общие сведения и подходы

Секреты — это данные, которые нельзя хранить в открытом виде или показывать пользователям. К ним относятся пароли, токены, закрытые ключи, строки подключения и внутренние ключи подписи.

Сертификаты используются для шифрования соединений и подтверждения подлинности сервисов. Сам сертификат обычно не является секретом, но связанный с ним закрытый ключ должен быть защищён.

В PVS применяется следующий подход:

- основное хранилище секретов — HashiCorp Vault;
- в production используется внешний Vault;
- встроенный Vault с одной репликой предназначен только для разработки и тестовых сред;
- сертификаты в Kubernetes обычно выпускает и обновляет cert-manager;
- секреты передаются сервисам через Vault, Kubernetes Secret, переменные окружения или файлы, смонтированные в контейнер;
- фактические значения секретов не должны отображаться в интерфейсе;
- секреты в журналах маскируются;
- повторный запуск установки не перезаписывает уже существующие значения в Vault.

Упрощённая схема работы:

1. Оператор передаёт начальные значения через `bootstrapSecrets`.
2. Установщик создаёт отсутствующие секреты или генерирует их случайным образом.
3. Значения записываются в Vault в режиме `write-if-absent`.
4. Сервисы входят в Vault под своими Kubernetes ServiceAccount.
5. Сервис получает необходимое ему значение или подготовленный Kubernetes Secret.
6. Сертификаты выпускаются и обновляются отдельно через cert-manager.

В Kubernetes каждый сервис имеет собственную Vault-роль. Срок действия получаемого Vault-токена составляет один час. При этом в текущей реализации все сервисные роли используют общую политику `pvs-services` с достаточно широким доступом ко всему дереву секретов платформы. Поэтому отдельная роль пока не означает строгую изоляцию секретов одного сервиса от другого.

## 2. Классы секретов

| Класс | Примеры | Простое описание |
|---|---|---|
| Сервисные пароли | PostgreSQL, LDAP, Grafana, OpenSearch | Используются сервисом для входа в другую систему |
| Учётные данные регионов | OpenStack и Kolla credentials | Позволяют управлять конкретным OpenStack-регионом |
| Токены | NetBox token, Vault token | Временный или постоянный ключ доступа к API |
| Клиентские секреты | Keycloak client secret | Подтверждают подлинность приложения при обращении к внешнему сервису |
| Внутренние общие секреты | HMAC, gateway secret | Позволяют сервисам проверять, что запрос отправил доверенный компонент |
| Ключи подписи | JWT secret | Используются для создания и проверки подписанных токенов |
| Строки подключения | PostgreSQL DSN, Redis URL, RabbitMQ transport URL | Содержат адрес сервиса и могут включать логин и пароль |
| SSH-ключи | Ed25519 private/public key | Используются worker-компонентами для подключения к управляемым узлам |
| TLS-ключи | `tls.key` | Закрытая часть сертификата; должна храниться как секрет |
| Сертификаты и CA | `tls.crt`, `ca.crt` | Подтверждают имя сервиса и формируют цепочку доверия |

## 3. Основные места хранения

| Место | Что хранится | Назначение |
|---|---|---|
| Внешний Vault KV v2 | Пароли, токены, HMAC, credentials, SSH-ключи | Основное хранилище production-секретов |
| Встроенный Vault на PVC | Те же типы секретов | Только для dev/test; в production отключён |
| Kubernetes Secret | TLS-ключи и сертификаты, производные сервисные секреты | Доставка данных непосредственно в Pod |
| `/app/certs` внутри контейнера | `tls.crt`, `tls.key`, `ca.crt` | Рабочая копия сертификата и ключа для запущенного сервиса |
| Переменные окружения | Разрешённые строки подключения и пути к сертификатам | Передача настроек приложению при запуске |
| `bootstrapSecrets` | Первичные значения для загрузки в Vault | Используются во время установки, а не как постоянное хранилище |
| Локальный каталог `cert/` | Начальный CA и сертификат Vault | Применяется в docker-compose/rpm до запуска Vault |

Стандартный полный путь в Vault имеет вид:

```text
secret/platformv/<путь-секрета>
```

Здесь `secret` — имя KV mount, а `platformv` — префикс платформы. Оба значения могут быть изменены настройками установки.

## 4. Сервисные пароли и секреты

Все пути в таблице указаны относительно стандартного префикса `secret/platformv/`.

| Путь в Vault | Содержимое | Для чего используется |
|---|---|---|
| `infrastructure/database` | Пароли PostgreSQL и строки подключения сервисов | Подключение backend, scheduler, nbox, hub, git-service, orchestrator и registry к базе данных |
| `infrastructure/redis` | `url` | Подключение backend, git-service и nbox к Redis |
| `infrastructure/rabbitmq` | `transport_url` | Подключение `pvs-openstack-agent` к RabbitMQ |
| `infrastructure/jwt` | `secret_key` | Подписание и проверка JWT-токенов |
| `infrastructure/hmac` | Набор HMAC- и gateway-секретов | Проверка внутренних запросов между сервисами |
| `infrastructure/celery` | Broker URL, result backend, control broker URL | Работа фоновых задач Celery |
| `infrastructure/opensearch` | `admin_password` | Подключение к OpenSearch |
| `ldap/pvs-local` | `bind_password` | Сервисное подключение backend к локальному LDAP |
| `integrations/ldap/corp-ad` | `bind_password` | Подключение к корпоративному Active Directory |
| `integrations/ldap/freeipa-lab` | `bind_password` | Подключение к FreeIPA |
| `integrations/grafana` | `admin_password` | Административный доступ Grafana |
| `integrations/keycloak` | `admin_client_secret`, `api_client_secret` | Авторизация backend при работе с Keycloak |
| `integrations/netbox` | `token` | Обращение backend к API NetBox |
| `kolla/regions/{region_id}/credentials` | Сервисные пароли Kolla | Управление сервисами конкретного OpenStack-региона |
| `openstack/regions/{region_id}/credentials` | Административные credentials OpenStack | Прямое обращение к API региона |
| `services/pvs-worker/ssh-keys` | `private_key`, `public_key` | SSH-доступ worker-компонентов к целевым узлам |

Некоторые секреты создаёт установщик, а некоторые должны быть переданы внешней системой или записаны отдельным сервисом:

- пароли БД, JWT, часть HMAC-секретов, OpenSearch, LDAP, Grafana, Keycloak, NetBox и SSH-ключи создаются или загружаются при установке;
- Kolla credentials записывает `pvs-openstack-hub`;
- OpenStack credentials должны поступать извне;
- дополнительные LDAP-провайдеры также должны быть предварительно заполнены оператором;
- Redis, RabbitMQ и Celery не заполняются стандартным `vaultseed.py`.

## 5. Управление сертификатами

В Kubernetes сертификатами управляет cert-manager.

Он создаёт:

| Тип | Состав | Назначение |
|---|---|---|
| Корневой CA | `pvs-ca`, Secret `pvs-ca-root` | Формирует внутреннюю цепочку доверия |
| 11 сервисных сертификатов | backend, frontend, scheduler, nbox, registry и другие сервисы | HTTPS и внутренний mTLS |
| 3 инфраструктурных сертификата | etcd, Redis, PostgreSQL | Защита подключений к инфраструктурным компонентам |
| Ingress-сертификат | `pvs-ingress-tls` | Внешний HTTPS для пользователей; создаётся при включённом ingress TLS |

Сервисные TLS-данные сохраняются в Secret с именем вида:

```text
<release>-<service>-tls
```

В контейнере Secret монтируется в `/app/certs`:

```text
/app/certs/tls.crt
/app/certs/tls.key
/app/certs/ca.crt
```

Срок действия корневого и сервисных сертификатов — 90 дней. Обновление начинается за 15 дней до окончания срока.

Если используется корпоративный CA или Vault PKI, можно указать внешний `Issuer` или `ClusterIssuer`. Если cert-manager отключён, оператор должен самостоятельно создать все 15 обязательных TLS Secret и дополнительный ingress Secret, если он используется.

Для docker-compose/rpm сертификаты выпускаются Vault Agent через Vault PKI. Начальный CA и сертификат самого Vault создаются командой `make cert`.

etcd использует отдельный mTLS-контур с собственными клиентскими сертификатами. Этот механизм не зависит от прикладной проверки заголовков `X-PVS-User`, `X-PVS-Roles` и `X-SSL-Client-CN`.

## 6. Защита значений секретов

Значения секретов не должны выводиться в пользовательском интерфейсе. Страница `/secrets` показывает только метаданные Vault.

В журналах используются правила маскирования для следующих данных:

- паролей;
- API-токенов и ключей;
- Vault-токенов;
- JWT и OpenStack Keystone-токенов;
- заголовков `Bearer`;
- закрытых SSH- и PEM-ключей;
- строк подключения с паролем;
- длинных hex- и base64-значений;
- Slack webhook URL.

Маскирование журналов является дополнительной защитой. Оно не заменяет правильное хранение секретов и ограничение доступа к Vault и Kubernetes Secret.

## 7. Важные ограничения текущей реализации

По `DOC.md` необходимо учитывать следующие особенности:

- отсутствие секрета не всегда останавливает сервис: часть компонентов продолжает запуск с резервным или пустым значением;
- ссылка `infrastructure/rabbitmq#transport_url` сейчас не разрешается в `pvs-openstack-agent` и передаётся приложению как обычный текст;
- отсутствие LDAP bind-пароля может выглядеть как неправильный пароль пользователя;
- повторный запуск `seed-vault` не выполняет ротацию: существующие значения не перезаписываются;
- отдельные Vault-роли сервисов используют общую широкую политику `pvs-services`;
- перед включением mTLS список разрешённых CN необходимо сверить с фактическим именем Helm release, иначе внутренние запросы могут получить массовые ошибки 401/403;
- сертификат не является секретом, но его закрытый ключ `tls.key` должен храниться и передаваться как секрет.

## 8. Краткий итог

Vault является основным источником сервисных паролей, токенов и ключей. Kubernetes Secret используется как способ доставки части этих данных в Pod. Сертификаты в Kubernetes выпускает cert-manager, а в docker-compose/rpm — Vault Agent через Vault PKI.

Главная задача оператора — заранее подготовить внешний Vault, заполнить секреты, которые не создаёт установщик, обеспечить выпуск сертификатов и контролировать их обновление. Отдельно необходимо организовать ротацию паролей и ключей, поскольку повторная установка платформы не заменяет уже существующие значения.
